# PostgreSQL 存储故障与恢复副本

## 故障证据（2026-09-17）

17:04左右，用户的postgresql16容器停止提供连接并反复重启。日志报告`could not write to file pg_wal/xlogtemp: No space left on device`。

原挂载源`/mnt/d/Docker/postgres16/data`位于Docker内部`/dev/sde`的136MB分区，当时使用98%，可用约2.9MB。这个路径不是Windows D盘；Windows磁盘剩余空间不能代表该挂载源的可用空间。目录同步新增资料期间触及容量限制，QMT历史接口返回空数据是另一项独立故障。

## 已准备的恢复副本

- 停止原postgresql16容器的重启循环，原数据目录、容器配置和账号均保留。
- 将停止后的数据完整复制到Docker命名卷`pfor_qmt_pgdata_recovery_20260917`；复制后、启动前逐文件`diff -qr`比对通过。
- 使用postgres:16-alpine在容器`pfor-qmt-pg-recovery-20260917`启动副本，仅绑定本机55437端口，未修改项目config.toml。
- 副本完成PostgreSQL自身恢复；连接检查、schema版本2、证券数量和任务检查点查询通过。目录已保存612个指数、4125个A股；目录任务检查点为4736，旧任务仍保留，历史K线仍0条。
- 副本数据卷位于Docker主数据磁盘，检查时可用空间约850GB。没有删除WAL、重置事务日志或用空库替换业务数据。

## 用户重建实例后的恢复（17:16）

用户随后自行重建并启动postgresql16，保持原连接方式；新实例改用`postgres16_data`命名卷，可用空间约849GB。新实例可以连接，但不存在pfor_qmt数据库，因此没有替换用户的新容器或修改其挂载配置。

已从恢复副本用pg_dump导出仅pfor_qmt schema的归档，在新实例创建空的pfor_qmt数据库，并以单事务pg_restore恢复。11张表按主键排序逐行比对完全一致，包含4737条证券、2802个板块、3个数据集、6个任务、179条覆盖记录及其他原记录。服务启动后从目录检查点4736继续，而不是重新创建任务。

恢复归档保存在本地`runtime/backups/pfor-qmt-recovery-20260917.dump`，不提交或打包。恢复副本容器已经停止，命名卷继续保留；没有删除原数据、WAL或任何业务记录。运行中的新实例继续使用原5432端口，项目config.toml未改动。

## 恢复后核验

目录任务已从4736续跑至7905/7905并完成，无名称缺失。当前证券为指数611个、A股5567个、ETF1727个；恢复时旧资料中510300.SH误标为指数，ETF同步已纠正，因此指数数量由612变为611。全部证券API分页与数据库逐条一致，三个类别小样本名称与QMT一致。历史K线仍0条，原历史链路阻塞不因数据库恢复而标记解决。
